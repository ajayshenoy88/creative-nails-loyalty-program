# Creative Nails Multi-Partner Loyalty Program

## Context

Creative Nails wants to run cross-promotion loyalty programs with nearby businesses (e.g., a gym in the same building). A partner business's customers get a sequence of discount codes for their first few visits to Creative Nails (e.g., 20% off visit 1, 15% off visit 2, 10% off visit 3 — tiered by visit number), or a flat discount for other partners. Codes are created per-customer (manually by staff/admin/business, or automatically when a customer self-enrolls), and redemption happens **in person only** — a staff member looks up the code at checkout and marks it used.

The user does not code, so this needs to be a small hosted web app operated entirely through simple dashboard pages, with no ongoing developer involvement for routine use. Their current site is WordPress on Hostinger — this new tool lives as a separate, linked web app rather than a WordPress plugin, since it needs its own database, auth, and logic.

Flows were reviewed with the user via a visual walkthrough (four-role flow diagram) before any code was written, and iterated across several rounds of feedback. Final decisions below.

## Roles

Four logins, all against the same underlying "enroll a customer + generate their program's codes" action, just scoped differently:

1. **Admin** — full control. Manages partners, programs/rules, code expiry, all logins (staff, business, and resetting a customer's PIN). Can also directly generate & assign codes to a customer under any business's program. **Supports more than one Admin login** — there's no assumption of a single owner; the app just protects against deleting the *last* remaining one (see Data Model), since there's no recovery path if every Admin login were gone.
2. **Staff (Creative Nails front desk)** — logs in to `/redeem` only. Looks up a customer by mobile or code, applies the discount, marks the code redeemed. This is the *only* way a code's status changes from active to redeemed, keeping redemption strictly in-person.
3. **Business (partner, e.g. the gym)** — one shared login per partner (not per employee). Can:
   - View their program's full customer roster (name, mobile, each code's status/expiry, discount) — for *every* customer enrolled under their program, regardless of whether they self-enrolled via the link, were added by the business, or were added by Admin.
   - View aggregate metrics (total enrolled, issued vs. redeemed per tier, redemption rate).
   - Assign a code directly to a specific customer (name + mobile) — e.g. enrolling a new gym member at the front desk.
   - Reference (not edit) their enrollment link/QR code.
   - **Cannot**: edit program rules/discounts/expiry, see other partners' data, **or touch anything on a customer's record** — no Change Number, no Reset PIN, no Block/Unblock, no editing a code's expiry date or status. Those all stay Admin-only. This matters specifically because Business's Customer view is built on the same underlying screen Admin uses (see Pages/Flows) — the exclusion has to be enforced by that screen checking who's viewing it, not just by never putting a link to it in Business's own navigation.
4. **User (customer)** — self-service via mobile number + a **6-digit PIN** they set themselves. No email, no SMS involved.

## Auth & Security

- **One shared login gateway** (`/login`) for all four roles, rather than separate URLs to remember — but not one single role-switcher screen. `/login` itself defaults straight to the Customer mobile+PIN form (no role picker visible at all, since customers are the overwhelming majority of visits) with a "Staff, Business, or Admin? Sign in here" link below it. That link leads to a **separate** screen with its own role picker (Staff / Business / Admin only — Customer isn't an option there, since that role already has its own default screen) and the same two-step mobile/PIN flow. This replaced an earlier single-screen design where a "Not a customer?" dropdown sat directly above the customer form — splitting it into two screens keeps the first thing every customer sees uncluttered by role-switching UI meant for a small minority of visits. Either way, the role choice is what tells the backend which table to check the credential against; it's never inferred from the credential itself.
- **There is no generic "Enroll" entry point on the login gateway.** Enrollment only ever happens via a partner's own specific link/QR code (`/enroll/[partner-slug]`, see Pages/Flows) — there's no legitimate destination for a plain "New customer? Enroll" button on the shared gateway, since the app would have no way to know which partner to enroll them into without one already being implied by the link they arrived on. An earlier mockup draft had such a button pointing at a hardcoded demo partner; it was removed once this was flagged, rather than building a "choose your business" directory screen for a need that hasn't actually come up.
- **Every role authenticates with a mobile number + 6-digit PIN — no passwords, and no separate username anywhere in the app.** Staff/Business/Admin use exactly the same identifier pattern as customers now (mobile number), not an invented username — there's no real reason to make someone remember an arbitrary login name when their own phone number does the job and Admin already has to collect it for contact purposes anyway. Chosen for consistency and simplicity over a mixed password/PIN system, accepting that a PIN is weaker than a full password — mitigated by the lockout below. If this ever proves too weak for Admin specifically (since that role controls the whole system), upgrading just that role to a real password is a small, isolated change.
- No SMS/WhatsApp anywhere in v1 — removes the Twilio account requirement entirely for launch. (Kept as a possible future add-on for optional notifications only, via a channel-abstracted `sendMessage()` so it's a small addition later, not a rewrite.)
- Customer PIN is chosen by the customer on first access (not required at creation time — Admin/Business can pre-create a customer+codes record without a PIN, and the customer sets their PIN the first time they look themselves up, "claiming" the account).
- **Login is genuinely two steps for every role, not mobile+PIN on one screen**: enter the mobile number first, then the app shows either "Enter your PIN" (one field — this identifier already has a PIN set) or "Set your PIN" (two fields, create + confirm, matching Enroll's pattern exactly) if it doesn't. This is what makes first-time claims *and* post-reset logins safe from a typo — there was no confirmation step here before the user asked "is this actually covered?," and it turned out it wasn't; the single combined mobile+PIN field couldn't tell claim-a-new-PIN apart from enter-an-existing-PIN, so it never asked twice.
  - **On the PIN step, the mobile number just entered is shown bold and noticeably larger than body text**, with a small edit-pencil icon beside it to go back and change it — not the small muted helper text + separate "Use a different number" text-link button used in an earlier build. The number the person is about to authenticate against should be the most visible thing on the screen while they're typing a PIN, not an afterthought in small grey type. Applies identically across all four roles' PIN-entry step.
- **No self-service forgotten-PIN flow, for any role.** If someone forgets their PIN, they ask Admin to reset it from the dashboard — acceptable since there's no SMS channel to verify identity automatically.
- **What "Reset PIN" actually does**: clears the stored PIN (sets it to unset), it does not generate and display a new one for Admin to relay. The next time that person logs in with their identifier, the two-step flow above naturally shows them "Set your PIN" — same claim flow a newly pre-assigned customer already goes through, no special-casing needed. Chosen over generating a random temp PIN for Admin to communicate, since relaying a secret verbally/by note is more error-prone and no more secure than just letting them set their own next time.
- **Changing a mobile number preserves the old one, rather than overwriting it** — see `secondary_mobile_number` in Data Model. The PIN is never affected by a number change, for any role.
- **Every delete action requires an inline confirmation** — not a native browser `confirm()` popup (looks and feels inconsistent with the rest of the app), and not a full-page navigation either. The row being deleted (e.g. a login) is replaced in place with "Delete Reception Desk? They will no longer be able to sign in." plus Cancel / Yes, delete buttons, so the consequence is stated in plain language at the point of action.
- **Lockout applies to every login type** (customer, staff, business, admin): 3 consecutive wrong attempts on a given identifier locks that identifier out for 30 minutes.
- **Public-enrollment abuse mitigation, decided**: code-generating actions performed by anything *other* than an authenticated Admin session — public (anonymous) enrollment, and Business's own Assign a Code — are rate-limited to **10 per hour per IP address**. Admin's own Assign a Code is exempt, since Admin is the one trusted/audited role everywhere else in the app too. Tracked via a small `code_generation_attempts` table (ip_address, created_at) — insert a row on every successful code-generating action, reject a new one if that IP already has ≥10 rows in the trailing hour. **The IP must be read from the platform-provided header** (Netlify's `x-nf-client-connection-ip`), never a client-suppliable one, or the limit is trivially bypassed by forging a header. This is a deliberate, proportionate mitigation, not a cryptographic guarantee — a motivated individual could still switch networks, and a busy gym's front-desk Wi-Fi could plausibly have several genuine members enrolling from the same public IP within an hour (10/hour was picked to comfortably clear that case for a single small-business location) — but it kills scripted/casual abuse, and the "a code is worthless until redeemed in person" backstop (see Roles) still holds underneath it regardless. Rejected attempts get a plain-language inline error ("Too many sign-ups from this connection — please try again later"), following the same inline-red-message convention as every other validation error.

## Data Model

- **partners**: id, name, contact info, active flag
- **programs**: id, partner_id, name, slug (optional direct link, see Pages/Flows), structure (`tiered` | `flat`), discount_type (`percent` | `flat_amount` — set once per programme, applies to every tier in it), rule config (JSON: tiered = ordered list of `{visit_number, discount_value}`; flat = single `discount_value`), default_expiry_days, status (`active` | `paused` | `stopped`), visible_on_main_link (boolean, default true)
  - **No separate `active` boolean** — an earlier draft had both a boolean and this 3-state `status` column before `status` existed in its final form; the boolean is redundant now that `status` fully covers it (`active` state doing the job the flag used to) and was left in by mistake. Just `status`.
  - `discount_value` is interpreted per `discount_type`: a `percent` programme's values are e.g. `20`/`15`/`10` (meaning % off); a `flat_amount` programme's values are e.g. `200`/`150`/`100` (meaning ₹ off). Chosen over mixing types within one programme's tiers — each programme is consistently "% off" or "₹ off" throughout, which covers wanting either kind per-partner without the added complexity of per-tier type switching.
  - **Tiered programmes have an explicit 4th "Visit 4+" tier**, not an overloaded "Visit 3+" — Visits 1/2/3 are each independently configurable, and Visit 4+ is its own field for the ongoing rate from then on (can differ from Visit 3's rate, e.g. ramping 20/15/10 then settling permanently at a lower rate). A `flat` structure is the same idea simplified to a single, always-recurring tier from visit 1.
  - **`status` has three states, not two**: `active`, `paused` (reversible — stops new sign-ups, Resume brings it back, existing codes unaffected), and `stopped` (permanent — same effect on new sign-ups as paused, but no Resume; running the offer again means creating a new programme). Stopping requires an inline confirmation since it's irreversible.
  - **`visible_on_main_link`**: whether this programme appears in the picker when a partner's primary link resolves to more than one active programme. Defaults true. Set to false for targeted campaigns (e.g. a referral programme) — otherwise every visitor to the general link would simply pick whichever open offer gives the deepest discount, defeating the point of a programme meant only for a specific audience. A programme with this set to false is still fully functional, just reachable only via its own direct link (see Pages/Flows).
- **customers**: id, partner_id, program_id, name, mobile_number, secondary_mobile_number (nullable), pin_hash (nullable until claimed), enrolled_by (`self` | `admin` | `business`), enrolled_at, blocked (boolean, default false — Admin-only; blocks login and redemption without deleting the record) (unique per partner+program on mobile_number, and separately on secondary_mobile_number)
  - **Changing a mobile number is a one-field edit that never touches anything else.** No code, redemption, or history is linked to the phone number string — everything is foreign-keyed to `customer_id`. So "what happens to their redemptions when the number changes" has a simple answer: nothing, because they were never attached to the number in the first place.
  - **`secondary_mobile_number`, not an overwrite of `mobile_number`.** When a customer's number changes, Admin sets it here instead of replacing the original — login then matches against either column (secondary checked first, falling back to primary), so *both* numbers keep working. This means the original is never lost, and the customer doesn't need staff to "restore" anything if they show up with their old phone. Deliberately doesn't support a *second* change (setting a new secondary just replaces whichever one was there) — a small history of every number someone's ever used isn't worth a second table for how rarely this comes up.
  - **Display convention wherever both numbers show** (Customer detail, Partner/business-login rows, the Logins list): primary number shown first, secondary shown second, each on its own line, each labeled "(primary)"/"(secondary)" — not run together on one line. This applies identically to `app_users.secondary_mobile_number` for staff/business/admin logins.
  - A single mobile number can have separate customer rows under different partners' programs at once (e.g. enrolled in both FitZone Gym and Sunrise Spa) — the Redeem page groups all of a mobile number's rows together.
  - **"One redemption per visit" is enforced per customer per calendar day, not per search result.** An earlier version of this only locked the sibling codes within the same search result view, which meant staff doing "Search again" for the same number reset the lock — a real gap the user caught by asking "what if staff searches again and redeems the other code?" The fix: once any code is redeemed for a customer, no other of their codes (across any partner) can be redeemed again until the next calendar day, checked against `codes.redeemed_at` — this persists across searches, logouts, and new staff sessions, not just within one lookup.
- **codes**: id, customer_id, program_id, visit_number, code (unique string), discount_type (`percent` | `flat_amount`, copied from the programme at issue time so it stays correct even if the programme's own type is edited later), discount_value, status (`locked` | `active` | `redeemed` | `expired`), expires_at (editable), redeemed_at, redeemed_by staff id
  - On enrollment/assignment, all codes for a program are generated at once: visit 1 = `active`, later visits = `locked` until the prior one is redeemed.
  - **Admin can override a code's `status` directly** (Active / Locked / Expired — not Redeemed, since that specific transition stays exclusively a Staff action via the Redeem flow, to keep its audit trail meaningful), independent of `expires_at`. This sits alongside the existing "set a past `expires_at` to force-expire" mechanism rather than replacing it — the two are separate, both legitimate, editable independently on Customer detail (an inline status selector next to the pill, and a separate expiry-date field with its own edit control).
  - **Once a code's status is `redeemed`, its `expires_at` is no longer editable at all** — there's nothing left to manage on that dimension once it's been used, so the edit control is hidden rather than just disabled-but-visible.
  - **Every place a code's expiry displays it as an exact date** ("Expires on 29 Aug 2026"), never a relative day-count ("Expires in 24 days") — and a redeemed code additionally shows the exact date it was redeemed, on its own line above the expiry line.
- **login_attempts**: identifier, attempt count, locked_until — used to enforce the 3-strikes/30-minute lockout across all login types
- **code_generation_attempts**: ip_address, created_at — one row per successful non-Admin code-generating action (public enrollment, Business's Assign a Code); used to enforce the 10-per-hour-per-IP cap (see Auth & Security). Admin's own Assign a Code doesn't write to this table at all, since it's exempt.
- **app_users**: id, name, mobile_number, secondary_mobile_number (nullable), pin_hash, role (`admin` | `staff` | `business`), partner_id (set only for `business` role, scopes their access)
  - No `username` column — `mobile_number` is the login identifier here too, same as customers, including the same secondary-number mechanism for when it changes (e.g. a business's contact number changes, or a staff member gets a new phone). Simpler than it originally was: fewer fields for Admin to fill in when creating a login (no need to invent a username), fewer fields for the person logging in to remember.
  - `role` renamed from `owner` to `admin` to match there now being more than one — no hierarchy between them, any Admin login has full access.
  - **App-level rule (not a column): the last remaining `admin` row can't be deleted.** Enforced in application code before the delete runs. Without this, it would be possible to delete every Admin login and lock the whole system out permanently, since there's no SMS-based account recovery.

## Pages / Flows

1. **Public enrollment pages — two link types, not one per campaign:**
   - **Primary: `/enroll/[partner-slug]`** — the one link a partner prints/posts and never has to change. If they have exactly one active *and visible* programme, it goes straight to that programme's enrollment form. If more than one is both active and `visible_on_main_link` (e.g. FitZone Gym's "New Member Welcome" and a second general offer simultaneously), it shows a lightweight "choose your offer" **picker** step first, then the form. Solves a real problem the user flagged: without this, a partner running multiple campaigns would need a separate physical QR code/poster per campaign and would have to reprint every time a campaign changes — the primary link stays constant regardless of what's currently active behind it. Programmes with `visible_on_main_link = false` (e.g. a referral offer) never appear in this picker — see the `programs.visible_on_main_link` note in Data Model for why that matters (otherwise everyone would just pick the deepest discount).
   - **Secondary: `/enroll/[partner-slug]/[program-slug]`** — an optional direct link to one specific programme, for when a business wants to promote a single campaign on its own (e.g. sharing a personal referral link) rather than through the general picker. Available on that programme's detail page in Admin/Business, not pushed as the default. This is also the *only* way to reach a programme that's hidden from the picker.
   - Either way: name + mobile number + 6-digit PIN, entered twice and matched (client-side in the mockup; must also be re-validated server-side — see Input Validation). On submit: creates the customer record, generates that program's codes (visit 1 active, rest locked), and **takes the customer straight to the same "my codes" view a returning customer sees after logging in** — not a separate one-off success screen, and with **no login-related UI anywhere on that view** (no mobile/PIN fields, no role picker — those only ever exist on the separate `/login` gateway, which the customer never sees again once they're on My Codes). There's no "start over" action on this screen for the same reason there isn't one after a normal login: the customer is now just using the app. Re-submitting an already-enrolled number signs them in instead of duplicating. All on-page copy (headline, offer breakdown) renders from that program's stored name/tiers — nothing about a specific campaign is hand-written into the page, so a new campaign never requires a content/code change, just a new program row.
   - **Both link types are now demonstrated end-to-end in the mockup**, not just described here: Programme detail's own enrollment link always previews as a Secondary/direct link (skips the picker, since visiting that specific programme's URL already says which offer). Business Home's enrollment link previews as whichever type matches its current programme filter — Primary/picker behavior when "All" is selected, direct behavior for whichever specific programme is selected — which is a mockup-only convenience (one UI element standing in for two different real URLs depending on filter state); in the actual product these are two textually distinct links, never the same element switching modes. A standalone side-by-side comparison of both flows also exists as its own artifact (tabs for "All Programmes" vs "Specific Programme"), built specifically so the two entry points could be reviewed next to each other without having to click through Business/Admin screens to trigger each one.
2. **Login gateway** (`/login`) — the single entry point for the other three roles plus returning customers, split across two screens rather than one role-switcher page. **`/login` itself shows only the customer mobile+PIN form**, since that's the overwhelming majority of visits, with a "Staff, Business, or Admin? Sign in here" link below it leading to a **separate** screen holding the Staff/Business/Admin role picker plus that role's own two-step flow. Submitting routes to that role's view below. This is the answer to "how does the app know who's logging in" — the person tells it, by picking their role, and the backend then only checks that credential against the matching table. No "Enroll" link lives on this gateway at all — see Auth & Security for why.
   - **Customer** → mobile number first, then either "Enter your PIN" or "Set your PIN" depending on whether one's already set (see Auth & Security) → "my codes": codes grouped by business, since one mobile number can hold codes from several unrelated partners at once (e.g. FitZone Gym and Sunrise Spa) — each business gets its own section with its own codes/status/expiry, not one flat list. Every code row shows its actual discount (e.g. "Visit 2 · 15% off"), an exact expiry date, and — for a redeemed code — the exact redemption date **on its own line above the expiry line**, never run together on one line.
   - **Staff** → redemption search, with the search field itself disappearing once a search runs. Search by mobile number or code; the search input and its icon-button are replaced by the results (or a "no customer found" message if nothing matches) plus a **Search again** action that brings the search field back — the field is never left sitting visible alongside stale results. Once a customer is found, **results show every code they hold, across every tier and every partner program they're in** — including already-redeemed and still-locked ones, each with its correct status pill **and its own expiry date** (every code gets `expires_at` at issue time regardless of status, so locked and active tiers show it exactly like the redeemed one does) — not just the single currently-redeemable code. Only the tier that's actually eligible right now gets an actual **"Redeem"** button (not "Apply & Redeem"); redeemed and locked tiers show only their pill (plus expiry), no action. Redeem requires an inline confirmation ("Redeem 15% off for FitZone Gym?") before it commits, and **the button disappears entirely once redeemed** — replaced by just a status pill, not left visible-but-disabled. **Only one code may be redeemed per visit** — redeeming any code locks every other eligible code for that customer for the rest of the day (see the `codes.redeemed_at`-based fix in Data Model), and this holds even after hitting "Search again" and looking the same customer up a second time — the locked state is re-shown, not reset. Redeeming records timestamp + staff id, and auto-unlocks the next tier's code in that program if any.
   - **Business** → titled **Home** (not "Dashboard" — a page title should read like a page, not an engineering label), scoped to their own partner_id, grouped into visibly distinct sections rather than one undifferentiated stack: the **programme filter** comes first (defaults to **"All"**, not a specific programme, showing combined stats across every programme they run — switchable to one specific programme for its own numbers), then directly below it the **enrollment link/QR for reference** — the partner's main link when "All" is selected, that specific programme's direct link when one is selected, with a small "Link for: [selection]" label so which link is currently showing is never ambiguous. The filter sits *above* the link deliberately: the link's content depends on the filter, so the control that changes it reads first. Below that, an **Overview** section (the enrolled/redeemed stat tiles) and a **Manage** section (two tiles — **Customers** and **Assign a Code**), visually separated so the page doesn't read as one long undifferentiated list.
     - **Customers** tile → the full roster, filtered the same way, newest enrollment first, **each row showing which programme/visit/discount the customer holds** (not just name+mobile+status pill — a business owner needs to see what was actually redeemed without guessing), with its own **"+ Assign a Code"** entry point near the top of the list, and each row linking into the **same underlying Customer detail screen** Admin uses (see the Customers & Codes note below) rather than a separate business-only detail implementation — **but scoped down for this role**: Business sees the same code list (programme/visit/discount, status, exact dates) read-only, with **no Change Number, Reset PIN, Block/Unblock, or code-status/expiry editing** — those stay Admin-only, since a business partner never had those rights in the first place (see Roles). The back navigation from that screen also returns to Business's own Customers list, not Admin's — this was a real bug in an earlier build (the shared-screen refactor initially gave Business every admin control *and* routed its back button into Admin's own Customers & Codes list, which chains to Admin's Partners/Programmes/Logins — i.e. a full permission leak — caught and fixed by adding a viewer-role flag the shared screen renders against). **Whatever hides the admin-only controls for Business must do so non-destructively** (CSS/`pointer-events`, not by nulling out the actual click handler) — an early fix disabled the code-status editor by overwriting its click handler with `null`, which meant a later Admin visit to the very same DOM element couldn't restore it either, since there was nothing left to restore. Toggling a class is safe to flip back and forth any number of times; overwriting the handler itself is a one-way trip.
     - **Assign a Code** → its own page: **programme select** + name + mobile — a partner running more than one programme at once has to say which one a new member is joining, the same reason Admin's assign page has a partner/programme picker; scoped to just their own programmes, unlike Admin's which spans every partner. Pre-filled from whichever programme was selected on the Home filter when they clicked through, defaulting to unset if "All" was selected. **On submit, shows a confirmation step** (who was assigned, which programme, their mobile number) with two explicit actions — **Done** (returns to the Customers list with the new entry sorted first) and **Assign Another Code** (resets the form in place for the next entry) — rather than a bare toast-and-redirect, so the person doing several assignments in a row isn't forced to re-navigate each time.
   - **Admin** → titled **Home** (same "Dashboard" → "Home" rename as Business, for the same reason), a hub not one long page: opens to an **Overview** section (partners, active programmes, total enrolled, redemption rate, redeemed this month) and a **Manage** section (the four tiles below), visually grouped rather than one undifferentiated stack of tiles and numbers. Each tile opens its own sub-page with a back icon (not a text "← Dashboard" link — back navigation is icon-only everywhere, see Visual Design) — and each of those drills down one level further into per-record detail pages, rather than editing everything from a single list:
     - **Partners** (list) → click a partner → **Partner detail**: business name (editable via a pencil icon next to the heading, inline expand-to-input-then-Save, not a separate page), its business login's contact mobile with **Change Number** and **Reset PIN** as icon actions directly on that row (not stacked full-width buttons — see Visual Design), a **Status** row showing an Active/Inactive pill with **Deactivate/Reactivate** as an inline text action beside it (reversible, so it applies instantly with no confirmation dialog — stops new sign-ups across all of that partner's programmes, doesn't touch codes already issued), its programmes list with **"+ Add another programme" pinned at the top** of that list (not the bottom, so it stays reachable regardless of list length), and the Bulk Upload entry point.
     - **Programmes** (flat list across every partner, plus the create form) → click a programme → **Programme detail**, reachable from here or from a Partner's page: its enrollment link/QR near the top (just below the title), an **Overview** section (enrolled/redeemed stats), a **Status** row (Active/Paused/Stopped pill) with **Pause/Resume** and **Stop** as inline text actions beside it — Pause/Resume is reversible and applies instantly, **Stop** is the one action here that still gets an inline confirmation, since it's genuinely irreversible (same "reversible = instant, irreversible = confirm" split as Partner Deactivate above) — then the full rule editor (structure, discount type, tier values, expiry, visible-on-main-link), with a single **Save changes** button that stays disabled until something on the form is actually edited (no clicking Save on an unchanged form). Its enrolled-customers roster is **not** a separate embedded list here — it's a single summary row ("2 enrolled · 1 redeemed") that links into the shared **Customers & Codes** screen pre-filtered to this programme (see below), so there's exactly one roster implementation in the whole app, not one per screen that shows customers.
     - **Customers & Codes** (browsable list, newest enrollment first, not just search) → click a customer, or use Search, → **Customer detail**: every code they hold across every programme they're enrolled in, showing the actual discount (e.g. "Visit 2 · 15% off"), an exact expiry date (not a relative day-count) **on its own line**, and — once redeemed — the exact redemption date too, **on its own line above the expiry line**, never run together. Each code has **one edit affordance — a pencil icon — that opens a single panel with both its expiry date and its status (Active/Locked/Expired) together, committed with one Save**, not two separate independent controls (an earlier version had the pencil edit only the date, with the status pill itself independently clickable to edit status — consolidated into one panel after the user pointed out status-editing should live under the edit icon, not scattered across two different tap targets). Redeemed is excluded from the status options, since that transition stays a Staff-only action via Redeem, keeping its audit trail meaningful. **The pencil icon itself is hidden entirely once a code is redeemed** — nothing on that code is editable anymore, date or status — and this needs enforcing at two layers: the icon is hidden per-code based on its own redeemed flag, *and* that per-code hide must be re-applied every time the screen's broader role-based visibility toggle runs (Admin vs. Business), because a blanket "show all admin controls" pass for Admin would otherwise blow away the specific redeemed-code hide underneath it — this exact bug shipped once and was caught by the user screenshotting a redeemed code with its edit panel open. The customer's mobile number row has **Change Number** and **Reset PIN** as icon actions, and a **Status** row shows Active/Blocked with **Block/Unblock** as an inline text action beside it (reversible, instant, no confirmation) — a blocked customer can't sign in or have codes redeemed, but their record and history are kept, not deleted. ## Input Validation

Every entry field needs both a client-side check (fast feedback) and a server-side check (the one that actually matters — client-side alone is never sufficient, since it's trivially bypassed). Rules, by field type, applied consistently everywhere that field type appears:

- **Mobile number** (every login identifier now — customer, staff, business, admin — plus partner contact mobile and assignment forms): exactly 10 digits, first digit 6–9 (Indian mobile format). Reject anything else with a specific inline message ("Enter a valid 10-digit mobile number"), not a silent failure.
- **6-digit PIN** (every role, every login/set-PIN moment): exactly 6 digits, numeric only.
- **PIN confirmation, actually built for every "set a new PIN" moment, not just Enroll**: self-enrollment, a pre-assigned customer's first claim login, and a post-reset login for any of the four roles all go through the same two-field create+confirm step, checked before submit with a specific "PINs don't match" message. This closed a real gap — the mockup originally only double-checked this on the Enroll form specifically, and the customer login form used one shared field for both "enter your existing PIN" and "set a new one," meaning a reset or first-time claim had nothing to catch a typo.
- **Names** (customer, contact, staff): required, reasonable max length (~100 chars) to protect layouts — deliberately *not* restricted to a narrow character set, since real names include apostrophes, hyphens, and non-Latin characters that a naive regex would wrongly reject.
- **Programme name**: required, reasonable max length (~60 chars).
- **Tier discount values**: `percent` type constrained 1–100; `flat_amount` type constrained to a positive number. Prevents nonsensical entries like "150% off" or a negative amount.
- **Default expiry / code expiry**: positive integer number of days; when editing a specific code's expiry date directly, a *past* date is deliberately still allowed — Admin force-expiring a code early is a legitimate action, not a bug to block.
- **Search fields** (mobile-or-code lookups): must be non-empty before the search action is enabled. Every search field has an explicit, visible search action (an icon button inside the field, or beside it) — never a silent "start filtering after N characters" behavior with no CTA, since that leaves the user unsure whether anything happened. After a search runs, the input clears itself so the field is ready for the next lookup rather than showing stale text.

**Every error message is plain language stating exactly what's wrong** ("Please enter a valid 10-digit mobile number," not "Invalid input"), and **shown inline in red directly below the specific field it belongs to** — never a generic banner, never the browser's own default validation bubble (which is inconsistent across browsers and not stylable). The mockup's `validateFields`/`showFieldError` pattern is built once and reused everywhere: Enroll, all four login-gateway forms, Add Partner, and Add Login all use it live (try leaving a field blank or entering a bad mobile number). The same two functions are what the real app's remaining forms (Assign a Code, partner/programme edits, searches) get wired to — this isn't a per-field custom build, it's one small reusable piece of logic applied consistently.

## Visual Design

Matches creativenails.in (WordPress/Kadence)'s palette. **Logo: the user supplied the actual current logo file (`creative_nails_logo.png`)**, which supersedes the earlier decision to skip the old logo mark over a palette mismatch — that concern was about a *different*, outdated file; this is the real one and is used on the sign-in screen. Fonts: Cormorant Garamond (headings) + Poppins (body), pulled directly from the live site's font files.

**Every icon and image asset must be self-contained — never a reference to a path on the local development machine.** Icons are inline SVG (in the mockup, JS-templated `<svg>` strings; in the real app, inline SVG or SVG React components), and the logo is embedded as a base64 data URI in the mockup. In the real Next.js app, the logo should instead be a committed, optimized static asset in the project (served via `next/image` or the `public/` folder) — the underlying rule is the same either way: nothing the shipped app renders may depend on a file path that only exists on whoever's laptop happened to build it, since none of that exists once deployed to Netlify. This was raised explicitly when the logo file was handed over and applies to every visual asset added from here on, not just this one.

Palette: white page/card background throughout. Color is a hierarchy, not decoration, with each hue doing exactly one job:
- **Primary/action — dusty rose (`#b76e79` fill, `#a45c68` hover)**: primary CTAs, active-state borders, the default status-pill color, and reversible secondary actions in their outline form (same hue, not a second color, so there's one color to learn for "this is a button").
- **Danger (`#D8434D`)**: reserved *only* for genuinely irreversible actions — deleting a login, stopping a programme permanently. Never used for anything reversible.
- **Reversible toggles are not danger-colored and don't get a confirmation dialog** — Pause/Resume a programme, Deactivate/Reactivate a partner, Block/Unblock a customer all apply instantly (rose, not red) since they can be undone with one more tap. Only truly irreversible actions (Stop a programme, Delete a login) get the inline "are you sure" treatment. This distinction came from a real mistake in an earlier mockup pass — Deactivate/Block were first built as danger-red with a confirm dialog, which was wrong on both counts and got corrected once flagged.
- **Status is always shown as a colored pill (a background), never bare text** — specifically so a status value sitting next to a text-link action (e.g. "Active [Deactivate]") can never be misread as another clickable action.

Mobile-first, responsive web app (runs in the phone browser at a normal URL) — explicitly not a native/app-store app. Dropdown (`<select>`) fields are styled to match text inputs exactly (same border/radius/padding/background), with only a custom chevron icon distinguishing them — not left at browser-default appearance.

**No dark mode.** The app is always white/light, regardless of the viewer's OS or browser theme setting. This was a deliberate correction: the review mockups initially auto-switched to a dark variant for anyone with dark mode enabled at the system level (matching Anthropic's own artifact-hosting default of supporting both), which confused the user into thinking the "make it white" decision had been abandoned. It hadn't — the white design was always the default — but supporting a second look at all wasn't worth the confusion for a single-brand app, so dark mode was removed entirely rather than just fixed.

**Terminology: "Code," not "Offer," everywhere** ("My Codes," "Assign a Code," code statuses). Explicitly revisited and confirmed — "Offer" describes the abstract deal (20% off); "Code" is the concrete redeemable thing a customer holds and staff looks up, which is literally what Redeem does. Noted here so it doesn't get re-litigated per-screen later.

### UX/Interaction Conventions

These came out of a dedicated design-principles pass plus several rounds of screen-by-screen feedback, and apply consistently across every screen, not just where they were first noticed:

- **Icon-row actions instead of stacked full-width buttons.** Anywhere a row/section needs 2–3 secondary actions (Change Number, Reset PIN, Delete on a login row; Change Number, Reset PIN on a contact-mobile row), they're icon buttons in a row, not buttons stacked on top of each other — with generous spacing between adjacent icons (~10–12px) so mis-taps aren't a real risk.
- **Inline edit/confirm states are stacked vertically, not crammed onto one row.** Context text on its own line, the input (if any) on its own line below, action buttons on their own line below that — never label + input + Save + Cancel all fighting for space on one row.
- **Confirmation-after-creation, not a bare toast.** Any "you just created/assigned something" moment (Add Login, Add Partner, Bulk Upload, Assign a Code) shows a dedicated confirmation screen summarizing what happened, with explicit next-step actions (e.g. Done / Assign Another) — not just a toast that fades before anyone's sure what occurred.
- **A full-form "Save" button starts disabled and only enables once something on the form actually changes** (dirty-state tracking) — applies to Programme detail's rule editor and should be the default for any similar multi-field edit screen added later.
- **Landing/home pages are titled "Home," not "Dashboard,"** and are visually grouped into labeled sections (e.g. Overview stats, Manage tiles) rather than one undifferentiated stack — a stat grid and a list of navigation tiles are different kinds of content and should read that way.
- **"Add" actions in a list sit at the top of that list, not the bottom** (e.g. "+ Add another programme"), so they stay reachable without scrolling regardless of how long the list grows.
- **Reference links (like an enrollment link tied to a filter/selector) are positioned near the top of the page, directly below whatever control determines their value**, with a small label naming what's currently selected — never floating ambiguously with no indication of which selection produced it.
- **One shared list+detail screen per entity, reused everywhere it's needed** (see Customers & Codes in Pages/Flows) rather than a separate roster implementation per context that happens to need "view enrolled customers."
- **Back navigation is icon-only, never a text link** ("← Dashboard"), and root/tab screens show their title in the top bar; sub-screens repeat the title as their own heading below it, not beside the back icon.

### Fixed: stale authenticated content reachable via browser back/forward after logout (bfcache)
- User reported, from real device testing, that using the browser's forward button after logging out could show a previous authenticated page instead of re-checking the session. Root cause: no cache-control headers existed anywhere, and auth was enforced only by each page's own session check — which only runs on an actual server request. Browsers can restore a page from the back-forward cache on back/forward navigation without making any request at all, bypassing that check entirely.
- Fixed with a no-store cache header on every route plus a small component that force-reloads whenever a page is restored from that cache, guaranteeing a real server round-trip (and therefore a real session check) every time.
- Verified directly: logged in, navigated to an authenticated page, logged out, then tested back/forward — confirmed it correctly lands on sign-in rather than restoring stale content. A sharp follow-up question from the user (shouldn't back go to the previous page, not sign-in?) led to redoing the test in a clean browser tab, which confirmed back-navigation with a valid session correctly goes to the immediate prior page as expected — the sign-in redirect only happens once the session is actually gone.
- **Caught a real regression before deploying, from the user asking "anything else to check?" rather than assuming the fix was risk-free**: the blanket no-store rule was also silently overriding Next.js's own long-term caching for its content-hashed JS/CSS bundles — meaning every navigation would re-download unchanged bundles from scratch, reintroducing a load-time regression of the exact kind fixed earlier this session. Confirmed via direct header inspection against a real production build, then fixed with a more specific rule restoring long-term immutable caching for those bundles only, while pages keep the no-store behavior.
- **Deployed to staging; user's own re-testing surfaced a second, more important regression**: overall speed hadn't improved and was actually worse specifically on back-button navigation. Root cause: the reload-on-restore logic fired unconditionally on every bfcache restore — but that near-instant restore is exactly what made back-navigation feel fast before; forcing a full server round-trip on every single back-press, even when nothing about the session had changed, traded away speed everywhere to fix a bug that only actually mattered right after logout.
- Fixed by adding a deliberately cheap session-validity check (no database call) that the reload logic now asks first — only forcing a reload when the session has actually become invalid, leaving fast back-navigation alone otherwise. Verified both halves directly (valid session: no reload, stays fast; invalid session: reload fires, correctly redirects). Not yet deployed — user asked to hold everything so testers can evaluate the currently-live version first; this fix and anything else will go out together in tomorrow's batch.

### Test case list

**Auth / login (all four roles)**
- Mobile number with no PIN set yet → shows "Set your PIN" (create + confirm), not "Enter your PIN."
- Mobile number with a PIN already set → shows "Enter your PIN" (single field), never the set-PIN step.

- Locked identifier tries again after 30 minutes → normal login form again, attempt counter reset.

- Business login's back button from that customer detail view returns to Business's own Customers list — never to Admin's cross-partner list or Admin Home.
- Business login cannot see or act on another partner's data under any URL it can reach.
- Admin login can do everything Business can, plus Change Number/Reset PIN/Block/Unblock/edit a code's expiry and status, deactivate/reactivate a partner, pause/resume/stop a programme, and manage all logins.
- Deleting the last remaining Admin login is blocked with an explanation, not the usual delete-confirm flow — verify this holds even via a direct API call, not just that the UI button is disabled.
- Staff login can only reach the redemption search — no access to Partners/Programmes/Customers & Codes/Logins.
- A Staff, Business, or Customer session cannot call any Admin-only API route directly (e.g. resetting someone else's PIN, editing a programme's rules) even with a hand-crafted request — this needs a server-side role check on every route, not just a hidden UI element.

**Code lifecycle & data integrity**
- Editing a code's expiry to a future date updates it and re-renders "Expires on [date]."
- Editing a code's expiry to a *past* date is allowed (not blocked as invalid) and flips that code's status to `Expired` automatically if it wasn't already `Redeemed`.
- A code's status (Active/Locked/Expired) can be set directly, independent of touching the expiry date.
- The status override never offers `Redeemed` as an option — that transition only happens through the actual Staff Redeem action.
- Once a code is `redeemed`, its edit control (expiry + status) disappears entirely — verify a direct API call to edit a redeemed code's expiry/status is also rejected server-side, not just hidden client-side.
- Changing a customer's mobile number (Change Number) sets `secondary_mobile_number` and leaves `mobile_number` untouched — login then succeeds with *either* number.
- All of that customer's codes/history remain attached and correct after a number change (nothing is keyed off the phone number string).
- Setting a second "new" number replaces whichever secondary was there before (no history of more than one prior number) — confirm this is the accepted behavior, not a bug.
- Blocking a customer prevents both login and redemption for that customer, but their record/codes/history are still visible in Admin/Business — never deleted.
- Unblocking reverses this immediately, no re-enrollment needed.
- Deactivating a partner stops new sign-ups on all of that partner's programmes but does not affect already-issued codes (they still redeem normally).
- Pausing a programme stops new sign-ups, existing customers/codes unaffected; Resume brings new sign-ups back.
- Stopping a programme is permanent — no Resume option appears afterward, and it requires the inline confirm before it commits.

**Validation (client *and* server — test both independently)**
- Mobile number field rejects anything that isn't exactly 10 digits starting 6–9, everywhere it appears (login, enroll, assign, partner contact, staff/business/admin creation).
- 6-digit PIN fields reject non-numeric input and anything not exactly 6 digits.
- Every "set a new PIN" moment (enroll, first claim, post-reset, for all four roles) requires the two PIN fields to match before submit.
- Tier discount values: `percent` type rejects anything outside 1–100; `flat_amount` type rejects zero/negative values.
- Programme name and person names are required and length-capped, but never rejected for containing apostrophes, hyphens, or non-Latin characters.
- Every validation error appears inline, in red, directly under its own field — never a top-of-page banner, never the browser's native validation bubble.
- **Server-side validation duplicates every one of the above independently of the client** — test this by bypassing the client (direct API calls with bad payloads) and confirming the request is still rejected with the same rules.

**Security**
- No PIN is ever sent or logged as a URL query parameter — only in POST bodies over HTTPS.
- PINs are stored hashed (bcrypt or equivalent), never plaintext, verified by inspecting the database directly.
- Session cookies are `Secure` and `HttpOnly`.
- A locked-out identifier's lockout state is enforced server-side (checked on every login attempt against the database), not just reflected in client UI state that a direct API call could bypass.
- **Rate limit is enforced**: 11th non-Admin code-generating action (public enrollment or Business Assign a Code) from the same IP within a rolling hour is rejected with the inline "too many sign-ups" message; the 10th still succeeds.
- Rate limit resets correctly after the rolling hour elapses (the oldest attempt ages out, a new one is allowed).
- Rate limit is enforced against the **platform-provided IP header**, not a client-suppliable one — confirm a forged `X-Forwarded-For` header on a direct API call doesn't bypass it.
- Admin's own Assign a Code never writes to `code_generation_attempts` and is never blocked by this limit, however many it does in an hour.
- The limit is shared across public enrollment *and* Business's Assign a Code for the same IP (one does count toward the other's cap, by design) — confirm this is the intended behavior, not a surprise.

**Concurrency / edge cases**
- The same mobile number enrolled under two different partners' programmes at once shows both, correctly separated, on "My Codes" and in Staff's redemption search.
- A customer with a `secondary_mobile_number` set can log in with either number, and Staff can find them by either number too.
- Two Admin sessions editing the same programme's rules at nearly the same time — confirm the second Save doesn't silently clobber the first without at least a stale-data warning (acceptable to accept "last write wins" for v1 given single-operator usage, but should be a deliberate choice, not an untested accident).
